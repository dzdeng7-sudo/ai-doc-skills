# 反向梳理 PRD：从现有系统代码到标准 PRD

场景：新产品或新成员要熟悉现有系统，靠人工截图找开发逐个确认效率太低。由你阅读当前系统的代码，把实际运行的功能反向梳理成标准 PRD。

模板位于本技能目录下 `assets/通用产品需求文档_PRD标准模板.md`。**开始整理前必须完整读取该模板**，严格按其章节结构输出：功能结构 → 业务描述 → 业务流程 → 功能规则（含状态表、权限表）→ 功能详情 → 各子功能的输入输出描述与页面操作语。

## 工作流程

1. **确定梳理范围。** 用户消息已明确到系统/模块/功能的，直接开始；只说"梳理系统"的，先快速浏览代码库结构，列出主要模块请用户选择，不要擅自全量输出。

2. **按线索通读代码。** 推荐顺序：
   - 入口层：路由、控制器、API 定义 → 模块的完整功能入口清单
   - 页面层：前端页面/组件 → 菜单结构、列表列、筛选条件、表单字段、按钮
   - 服务层：业务逻辑 → 状态流转、校验规则、计算口径、异常与重试分支
   - 数据层：表结构、字段、枚举、字典 → 每个界面字段的取值来源与格式
   - 权限与配置：权限点、角色、配置项 → 权限差异表的内容

3. **只写有依据的事实。** 模板自身的输出要求是最高优先级：
   - 只记录代码中实际存在的当前行为，每条规则、每个字段、每个按钮都要有代码依据
   - 不写未来方案、改进建议；不推测代码中无法确认的业务规则
   - 代码读不出、无法确认的信息直接略过，不编造填补；在**对话回复中**（不写进文档）汇总"未能从代码确认的点"，供用户找相关开发核实

4. **按模板清理格式。** 输出时删除模板中的"填写说明"段落、示例行和不适用的小节；标题编号按实际内容连续调整；适用的小节不留空，按要求写实。

## 输出

- 保存为 markdown 文件，命名如 `PRD_<系统或模块名>.md`，放在当前工作目录或用户指定位置
- 覆盖多个模块时，每个模块对应模板的一个 1.X 节
- 梳理对象可以是整个系统、某个模块或单个功能
