# 文档只写最终方案（Final Solution Only）

文档是系统最终状态的快照，不是决策过程的记录。读者想知道"系统现在是什么样"，而不是"哪些方案被否决过"。因此修改文档时，把文档当成"被删除的方案从未存在过"来处理。

## 核心规则

1. **只写"是什么"，不写"不是什么"。** 每句话陈述最终采用的设计。一种技术被移除后，它在文档中的唯一痕迹是"不再出现"，而不是"一句否定它的句子"。

2. **删除要删干净。** 移除某个方案/技术/配置时，同步清理：
   - 相关段落、小节标题、表格行、图、示例代码、文档内的注释说明
   - 目录、交叉引用、"见 XX 节"等指向它的引用
   - 不留空标题，不写"（此处略）"之类占位符

3. **禁止以下句式**出现在文档中（用户明确要求的对比/范围章节除外，见下文）：
   - "未使用 / 不使用 / 不采用 / 无需 XX"
   - "已移除 / 已删除 / 不再使用 / 弃用 XX"
   - "暂不使用 XX（后续可能引入）"
   - 任何强调某种技术或方案"缺席"的否定句

## 示例

用户要求："不用配置表了，改成环境变量。"

好的写法：

> 相关参数通过环境变量 `APP_CONFIG` 注入，服务启动时加载。

不好的写法（禁止）：

> 本设计不使用配置表，相关参数通过环境变量 `APP_CONFIG` 注入。

## 允许提及被移除方案的例外

只有用户明确要求时，才在用户指定的章节里描述备选或被移除的方案，且只客观陈述、不贬低：

- "方案对比 / 技术选型"章节：客观陈述各方案的取舍。
- "非目标 / 范围"章节：陈述系统边界属于正常内容。
- 文档自带的"变更记录"章节：可记录事实性变更（如"配置方式改为环境变量"），但不写否定性评价（如"删除了多余的配置表"）。

这些章节必须由用户明确要求才存在，不要自行添加。

## 修改完成后自查

1. 全文搜索被删技术的名称，确认正文不再出现（除非位于上述例外章节）。
2. 确认没有残留的空标题和悬空引用。
3. 重读本次新增或改动的句子，确认没有否定句式混入。
4. 在对话中向用户汇报改动时，说明"删除了哪些内容"即可，同样不必补充"文档中没有 XX"这类句子。
