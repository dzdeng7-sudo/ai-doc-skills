# 内容范围：只写用户点名的内容

用户要求什么就写什么。自作主张补充"相关话题"（如清结算方案里提商户 KYC 进件、部署文档里顺带写监控体系）会让文档偏离主题、夹带用户不需要的内容，还会增加评审负担。

## 核心规则

1. **内容范围 = 用户点名的主题、章节、技术点。** 未点名的话题、模块、技术一律不写，即使你认为它们"相关"或"配套"。

2. **禁止这些行为**：
   - 顺带提及用户未要求的相关模块或功能，哪怕一句"可与 XX 联动""依赖 XX 结果"
   - 自行添加用户没要求的章节：如"未来规划""扩展方向""生态集成""相关系统介绍"
   - 把用户的要求扩大化：用户要"改造方案"，就不要额外铺陈"现有系统全景"

3. **"少写 / 不写 / 后面另有讨论"的执行方式是让话题消失。** 用户让你略过某个话题时，正确结果是文档中完全没有它——既没有相关内容，也没有"XX 由专项另行讨论""本材料不涉及 XX""细节不在本文范围内""本材料只呈现 X"这类排除性说明和范围声明。这些是关于"文档本身写了什么"的元话语，对读者没有信息量。

4. **认为某内容很重要时，写进对话回复，不写进文档。** 例如："方案里没提 KYC 进件，如果结算依赖进件状态，需要补一节，要加吗？"——是否纳入由用户决定。

5. **唯一例外**：正文中使用了用户未点名的关键概念，不解释就读不懂时，可以最小限度定义该术语（一句话），不展开成段落或章节。

6. **修改已有文档时同样适用**：只做用户要求的修改，不趁机补写"缺失"的相关内容。

## 示例

用户要求："写一份清结算改造方案文档。"

好的做法：文档只覆盖清分、结算、出款、对账等与清结算直接相关的内容。

不好的做法（禁止）：在方案里加一段"本方案与商户 KYC 进件模块联动，进件完成后自动触发首期结算"——用户没有要求涉及 KYC。

又例如用户说"数据同步不用过多描述，后面有专项讨论"——

好的做法：文档中完全不出现"数据同步"相关内容。

不好的做法（禁止）：写一句"数据同步机制的细节由同步专项另行讨论，本材料只呈现方案与结果形态。"——话题没有消失，只是被声明性地提了一下。

## 适用范围

本规范同样适用于 HTML 页面、演示文稿、代码等各类产出：页面只呈现用户要求的板块，不自行加"了解更多""相关推荐"类内容。
